# 第二篇 · 一次读文件任务，消息到底怎样传递？

学习路线：[[00-Agent开发实习学习路线与项目规划]]。上一篇：[[01-pi-and-agent-harness]]。

你对助手说“读取 lesson.txt”，最后看到了文件内容。但在这两句话之间，程序和模型还交换了哪些信息？

这一篇把中间过程打开来看。先用普通话讲清楚每一步，再把它写成数据，逐项解释里面的名称和值。读完后，你应当能沿着一份记录回答：用户问了什么，模型要求做什么，工具实际返回了什么，最后的回答有没有依据。

**文中的文件内容、调用编号、回复和日志都是教学示例，本次没有实际运行这些任务。** 展示数据时，主要使用本地 Pi 的字段名称，只保留当前要讲的部分，省略时间戳、模型信息等字段。因此，这些片段可以帮助阅读，但还不能直接当作完整接口请求使用。第 9 节会用具体例子说明格式差异。

## 1. 先用普通话走完一次读文件任务

假设 Pi 当前工作的目录里有一个短文件 `lesson.txt`，完整内容是：

```text
今天学习 Agent。模型提出工具调用，程序执行工具。
```

你向助手提出：

> 请读取 lesson.txt，告诉我文件里的内容。

这次假设模型选择了读取工具，而且文件读取成功。整个过程可以读成下面四句话：

| 阅读标签 | 谁提供这句话或这份信息？ | 用普通话怎样表达？ |
| --- | --- | --- |
| A：用户问题 | 你 | 请读取 lesson.txt，告诉我文件内容。 |
| B：工具调用 | 模型 | 请执行 read，读取 lesson.txt。 |
| C：工具结果 | 读取工具返回数据，Pi 整理成消息 | 文件读到了，里面的文字是这些。 |
| D：最终回答 | 模型 | 根据刚才读到的文字，向用户回答。 |

Pi 把它们连接起来：先带着 A 请求模型，得到 B；再执行 B 要求的读取，得到 C；最后带着 A、B、C 再次请求模型，得到 D。

所以，这个例子里有 **两次模型请求、一次文件读取**。第一次模型决定先读取文件，第二次根据读取结果回答。后面每节都沿用 A～D 这四个标签，逐步查看消息里到底有什么。

## 2. 你输入的一句话，怎样变成消息？

你在聊天框里输入的，仍然是一句普通的话：

> 请读取 lesson.txt，告诉我文件里的内容。

程序收到后，需要把这句话和它的来源一起记录下来，例如：

| 要记录的信息 | 本例中的值 |
| --- | --- |
| 这是什么角色发来的消息？ | 用户 |
| 消息内容是什么？ | 请读取 lesson.txt，告诉我文件里的内容。 |

把这两项信息写成程序便于处理的数据，就可以得到下面的形式：

```json
{
  "role": "user",
  "content": "请读取 lesson.txt，告诉我文件里的内容。"
}
```

这种写法叫 **JSON**，是一种用文字表示数据的格式。**用户不需要手写这段 JSON，程序会负责组织这些信息。** 这里用 JSON 展示消息，是为了方便看清字段；程序内部也可以用对象等形式保存数据，并不要求所有消息都先变成 JSON 文本。

**先把两行内容读成两句话。**

- `"role": "user"`：这条消息的角色是用户。`role` 是这项信息的名称，`user` 是填入的值。
- `"content": "请读取 lesson.txt，告诉我文件里的内容。"`：这条消息的内容是这句话。`content` 是名称，后面的整段文字是值。

这些信息项通常叫**字段**。冒号把字段名称和值连接起来，逗号把不同字段分开。`role` 只区分用户、模型等消息角色；具体是哪位飞书用户发来的，还需要应用另行识别。

**再认识后面会用到的几种写法。**

| 写法 | 名称 | 可以怎样理解？ |
| --- | --- | --- |
| `{ ... }` | 对象 | 把相关信息放在一起，例如一条消息的角色和内容；这里的省略号仅用于示意 |
| `"lesson.txt"` | 字符串 | 一段文字，JSON 用双引号包住它 |
| `[ ... ]` | 数组 | 一个按顺序放置多项内容的列表；省略号同样只是示意 |
| `true`、`false` | 布尔值 | 表示是或否；例如后面的 `"isError": false` 表示没有标记为错误 |

例如，数组可以写成这样：

```json
["第一项", "第二项", "第三项"]
```

这个例子只是三段文字组成的列表。后面看到 `messages: [...]` 时，列表里放的是一条条消息对象；看到 `content: [...]` 时，列表里放的是这条消息的各部分内容。遇到它们时，我们会结合具体例子再解释。

JSON 的字段名和字符串都使用双引号。本文标为 `json` 的数据块都能作为 JSON 解析；完整接口需要哪些字段，还要按对应协议准备。[JSON 对象与字段说明](https://json-schema.org/understanding-json-schema/reference/object)

**理解练习。** 用户把问题改成“读取 homework.txt”，程序应该修改哪个字段？`role` 会变吗？

**参考答案。** 把 `content` 的值改成“读取 homework.txt”。`role` 仍然是 `user`，因为消息内容变了，发出问题的角色仍然是用户。

## 3. 第一次请求：Pi 要给模型准备哪三类信息？

现在，Pi 已经收到了用户问题 A。接下来要请求模型。为了让模型知道怎样处理，程序可以准备三类信息：

| 要交给模型的信息   | 用普通话表达                    | 本文使用的字段名       |
| ---------- | ------------------------- | -------------- |
| 处理任务的基础要求  | 先读取，再根据实际结果回答；失败时说明情况。    | `systemPrompt` |
| 用户的问题和已有交流 | 用户要求读取 lesson.txt。        | `messages`     |
| 可以使用的工具说明  | 有一个 read 工具，告诉它路径就可以要求读取。 | `tools`        |

下面分开看这三部分。每段都是字段摘录，实际请求会把相关信息组织到一起。

### 3.1 先说明处理要求

```json
{
  "systemPrompt": "回答文件内容前先读取文件；读取失败时说明情况，不要编造。"
}
```

`systemPrompt` 保存程序给模型的基础要求，也就是前面学过的系统提示。在这个例子里，它说明回答应当根据实际读取结果。

以后还可以加上回答方式，例如“先写读取状态，再写文件内容”。但写了要求之后，仍要检查模型是否按要求行动；实际文件权限也要由程序或运行环境限制。

### 3.2 再放入用户问题

```json
{
  "messages": [
    {
      "role": "user",
      "content": "请读取 lesson.txt，告诉我文件里的内容。"
    }
  ]
}
```

这一段可以从外向里读：`messages` 是消息列表；`[]` 里面放了一条消息；这条消息的角色是 `user`，内容是用户的问题。

这就是第 2 节的消息 A，只是在外面增加了一个列表。第一次请求里还没有文件文字，因为工具尚未执行。

### 3.3 最后说明工具能做什么、需要填写什么

要使用读取工具，模型需要知道下面这些信息：

| 信息 | 本例中的含义 |
| --- | --- |
| 工具名称 | read |
| 工具用途 | 读取指定路径的文本文件 |
| 必须提供的参数 | path，也就是文件路径 |
| 参数的要求 | path 的值必须是文字 |

写成数据后，一个工具说明可以是这样；这个对象会放进 `tools` 列表：

```json
{
  "name": "read",
  "description": "读取指定路径的文本文件，返回文件文字或错误。",
  "parameters": {
    "type": "object",
    "properties": {
      "path": {
        "type": "string"
      }
    },
    "required": ["path"],
    "additionalProperties": false
  }
}
```

先看外面三项：`name` 写工具名称，`description` 写用途，`parameters` 写参数的填写规则。

`parameters` 里面的写法叫 **JSON Schema**，可以先理解为“程序也能检查的填写要求”：

| 字段 | 在这里怎样读？ |
| --- | --- |
| `type: "object"` | 调用参数整体应当是一个对象，也就是用 `{}` 放在一起的一组信息。 |
| `properties` | 在这里列出参数字段，以及各自的要求。 |
| `path` 下的 `type: "string"` | path 的值必须是文字，例如 lesson.txt。 |
| `required: ["path"]` | path 必须填写，不能遗漏。 |
| `additionalProperties: false` | 这个教学工具不接受规则之外的其他参数字段。 |

这里先把工具简化为读取短文本。真实 Pi 的内置 `read` 还接受起始行、最多读取行数等参数。[本地读取工具定义](../../pi/packages/coding-agent/src/core/tools/read.ts)

工具说明告诉模型“怎样提出读取要求”。真正打开文件的函数仍在程序里，由 Pi 根据工具名称找到并调用。仅仅把上面的说明交给模型，还没有发生读取。

**理解练习。** 给模型的说明里有一个 read 工具，但程序里没有对应的读取函数，能读出文件吗？

**参考答案。** 不能。模型可以按说明提出调用，但 Pi 还需要找到真正执行读取的程序。工具说明负责描述能力，工具函数负责完成操作。

## 4. 模型的第一次回复：工具调用长什么样？

模型看完问题和工具说明，决定先读取文件。它提出的操作 B，用普通话表达就是：

> 请执行 read，把 lesson.txt 的内容读出来。这次调用编号记为 call_1。

程序需要从这句话里明确取得三项信息：用哪个工具、传入什么参数、这次调用用哪个编号标识。按本例约定，模型会用结构化工具调用来表达。Pi 中相应的消息字段可以写成下面这样：

```json
{
  "role": "assistant",
  "content": [
    {
      "type": "toolCall",
      "id": "call_1",
      "name": "read",
      "arguments": {
        "path": "lesson.txt"
      }
    }
  ]
}
```

先看最外层：`role: "assistant"` 说明消息来自模型。`assistant` 是这里对模型回复使用的角色名称。

再看 `content: [...]`：这一条消息的内容用列表来保存，列表里的每一项叫**内容块**。一条消息可以包含文字、工具调用等不同部分；这里先只放一个工具调用块。

最后看内容块里的字段：

| 字段                   | 在本例中的意思                              |
| -------------------- | ------------------------------------ |
| `type: "toolCall"`   | 这一块表示“要求调用工具”。                       |
| `id: "call_1"`       | 这次调用的编号是 call_1，后续结果会引用它；这个编号值是教学示例。 |
| `name: "read"`       | 要使用 read 工具。                         |
| `arguments`          | 这里放本次调用实际填写的参数。                      |
| `path: "lesson.txt"` | 本次填写的路径是 lesson.txt。                 |

第 3 节里的 `parameters` 和这里的 `arguments`，可以对照着记：

| 工具说明中的要求：parameters | 本次调用填写的值：arguments   |
| ------------------- | -------------------- |
| 必须提供 path，而且它必须是文字。 | path 填写为 lesson.txt。 |

`type` 也要结合位置理解。第 3 节的 `type: "string"` 在规定参数的数据类型；这里的 `type: "toolCall"` 在说明这一块消息是什么内容。字段名称相同，所在位置和用途不同。

**到这里，模型只是提出了操作，文件仍未被读取。** Pi 接下来才会按名称找到工具、检查参数，并调用实际函数。[本地工具调用与模型消息类型](../../pi/packages/ai/src/types.ts)

**理解练习。** 模型只回复一段普通文字“我准备读取 lesson.txt”，程序就会读取吗？

**参考答案。** 在本文采用的工具调用方式中，不会。还要产生程序能够识别的工具调用，并由 Pi 执行。判断有没有读取，要继续看后面的执行记录和结果。

## 5. 工具执行之后：怎样告诉模型“读到了什么”？

Pi 收到操作 B 后，找到 read 工具，并根据参数确定要打开的文件。假设这次成功读出了第 1 节的完整文字，接下来要把结果记录下来：

| 要记录的信息   | 本例中的值                       |
| -------- | --------------------------- |
| 这是哪一类消息？ | 工具结果                        |
| 对应哪次调用？  | call_1                      |
| 使用了哪个工具？ | read                        |
| 实际返回什么？  | 今天学习 Agent。模型提出工具调用，程序执行工具。 |
| 是否标记为错误？ | 否                           |

Pi 把这些信息整理成消息 C，字段摘录如下：

```json
{
  "role": "toolResult",
  "toolCallId": "call_1",
  "toolName": "read",
  "content": [
    {
      "type": "text",
      "text": "今天学习 Agent。模型提出工具调用，程序执行工具。"
    }
  ],
  "isError": false
}
```

这次也从外向里读：

- `role: "toolResult"`：这是一条工具结果消息。
- `toolCallId: "call_1"`：它回答的是编号为 call_1 的那次调用。
- `toolName: "read"`：结果来自 read 工具。
- `content` 中的 `type: "text"`：这部分结果是文字，具体文字写在 `text` 字段里。
- `isError: false`：这次操作没有被标记为失败。`isError` 可以读成“是否出错”，false 表示否。

**调用里的 `id` 和结果里的 `toolCallId`，要对应到同一次操作。** 在本例中，它们都填写 call_1：

```text
模型提出操作：id = call_1
工具返回结果：toolCallId = call_1
```

为什么还要有编号，只写 read 不行吗？假设同一个任务要求读取两个文件：

| 调用编号 | 工具名称 | 读取目标 | 对应的结果编号 |
| --- | --- | --- | --- |
| `call_1` | read | lesson.txt | `toolCallId = call_1` |
| `call_2` | read | homework.txt | `toolCallId = call_2` |

两个调用都使用 read，只看工具名称无法区分。通过编号，程序才能知道某份结果对应哪次操作。即使读取失败，错误结果也需要保留对应编号。[本地结果消息组装代码](../../pi/packages/agent/src/agent-loop.ts)

结果没有标记错误，还需要核对读的是不是目标文件。例如，另一个目录也有 lesson.txt，成功打开它也可能读错文件。长文件还可能只返回一部分；本篇暂时假设短文件已完整返回。

**理解练习。** 一条结果写着 `toolName: "read"`、`toolCallId: "call_2"`，应该先找哪条调用？

**参考答案。** 找 `id` 为 call_2 的调用，再查看那条调用的路径参数。不能因为它也使用 read，就把结果配给 call_1。

## 6. 第二次请求：把刚才的操作和结果一起交回去

读取工具执行完后，文件文字先回到 Pi。模型还需要收到这些文字，才能根据它们回答。

第二次请求时，Pi 把三条相关消息按顺序放入 `messages`：

| 顺序 | 消息 | 模型从中知道什么？ |
| --- | --- | --- |
| 第一条 | A：用户问题 | 用户要读取哪个文件、希望得到什么回答。 |
| 第二条 | B：模型提出的调用 | 刚才要求执行 read，路径是 lesson.txt，编号是 call_1。 |
| 第三条 | C：工具返回的结果 | call_1 对应的操作实际返回了哪些文字，有没有报错。 |

可以把它读成下面这段交流：

> 用户：请读取这个文件。  
> 模型之前的调用：请读取 lesson.txt，调用编号是 call_1。  
> 工具结果：call_1 对应的文件读到了，文字是这些。

这时，第二次请求比第一次多了**刚才的操作和实际结果**。基础要求、工具说明和模型配置仍由程序准备。需要对照完整列表时，再展开下面的数据。

```json
[
  {
    "role": "user",
    "content": "请读取 lesson.txt，告诉我文件里的内容。"
  },
  {
    "role": "assistant",
    "content": [
      {
        "type": "toolCall",
        "id": "call_1",
        "name": "read",
        "arguments": { "path": "lesson.txt" }
      }

    "role": "toolResult",

        "type": "text",
```

模型拿到这些信息后，可以生成回答 D。例如下面这条消息：

```json
{
  "role": "assistant",
  "content": [
    {
      "type": "text",
      "text": "lesson.txt 的内容是：今天学习 Agent。模型提出工具调用，程序执行工具。"
    }
  ]
}
```

它和第 4 节一样，角色都是 `assistant`，因为两次回复都来自模型。区别在于这次内容块的 `type` 是 `text`，里面放的是回答文字；上一次则是 `toolCall`，里面放的是操作要求。

到这里，文件文字已经进入模型本次参考的资料，也就是上下文。如果工具结果只显示在终端中，没有进入后续请求，模型这次就没有获得这份资料。

**理解练习。** Pi 读到了文件，但第二次请求只发送“请继续回答”，没有附带历史或结果。在本篇的流程中，模型能据此知道文件内容吗？

**参考答案。** 不能。“请继续回答”没有包含文件文字。程序要把相关消息交给模型。某些服务支持保存会话状态或引用历史，使用这些接口时也要按对应协议提供关联信息，不能只凭“上次请求过”就假定资料仍然可见。

## 7. 文件不存在时，哪条消息发生变化？

现在换一个情况：用户还是要求读取 lesson.txt，模型也照样提出 read 调用，但工具打开文件时发现文件不存在。

这时，A 和 B 可以与成功时相同。最先变化的是 C，也就是工具结果：

```json
{
  "role": "toolResult",
  "toolCallId": "call_1",
  "toolName": "read",
  "content": [
    {
      "type": "text",
      "text": "文件不存在：lesson.txt"
    }
  ],
  "isError": true
}
```

把它与成功结果对照，主要看两处：

| 要看的字段          | 读取成功时          | 文件不存在时        |
| -------------- | -------------- | ------------- |
| `content` 中的文字 | 返回文件内容。        | 返回文件不存在的错误说明。 |
| `isError`      | false：没有标记为失败。 | true：标记为失败。   |

`toolCallId` 仍然是 call_1，因为失败的就是刚才那次调用。“文件不存在：lesson.txt”是简化的教学文字，真实错误可能包含错误码和完整路径。

Pi 把错误交回模型后，模型就知道：刚才尝试了读取，但没有拿到文件内容。它可能告诉用户“没有找到文件，请确认路径”；如果有查找工具并且规则允许，也可能继续查找。**读取失败后，仍可能有下一步；这份错误不能作为已经读到文件文字的依据。**

排查问题时，可以先问“失败发生在哪一步”：

| 看到的情况             | 怎样理解和检查？                           |
| ----------------- | ---------------------------------- |
| 模型要求读取，但没有填 path  | 参数检查可能先失败，文件还没被打开。先看调用里填了什么。       |
| 调用了 read，返回文件不存在  | 已经尝试按路径读取。检查工具实际查找的位置。             |
| 请求模型时网络连接失败       | 出错的是与模型服务通信的步骤。查看请求错误，不能把它当成文件不存在。 |
| 工具读出了正确内容，最终回答却不对 | 检查这些文字是否进入后续请求，再对照模型回答。            |

### 一个与简历项目相关的例子

以后做旧改交付诊断时，可以把 read 换成 `get_node_history`，用它查询整改和复验记录。两种结果需要分清：

- **查询成功，相关记录为空**：在明确的查询范围内，没有查到记录；还要确认范围和数据完整性。
- **查询失败**：这次没有拿到可靠结果，还不能判断有没有复验记录。

例如，业务接口超时，不能据此回答“没有复验，所以不能交付”。应当说明当前无法核实，再按规则重试或请求进一步确认。

**理解练习。** 文件不存在时，把 `isError` 从 true 改成 false，能让读取成功吗？

**参考答案。** 不能。这个字段是在记录结果，改写它不会让不存在的文件出现，反而可能使程序或模型误判。状态标记应该与实际执行结果一致。

## 8. 把消息交给模型时，还会遇到哪些设置？

前面已经看清“交给模型什么内容”。真正接入服务时，还要决定使用哪个模型、允许多长的输入输出，以及怎样接收回答。下面继续结合读文件来理解，具体接入代码留到第三篇。

### 8.1 同一句问题，发给哪个模型？

假设问题仍然是“读取 lesson.txt”。程序还需要知道：

| 配置信息 | 回答的问题 |
| --- | --- |
| 模型服务地址 | 请求发到哪里？ |
| API 密钥 | 这次请求用什么凭据访问服务？ |
| 模型名称 | 请这个服务里的哪个模型处理？ |
| 生成设置 | 希望生成时采用哪些参数？ |

这些信息与“用户要求读取哪个文件”各有用途。密钥用于服务认证，应从安全的配置位置读取，不要把它写成普通消息发给模型。

以后比较项目改动前后的效果，除了记录问题和工具结果，也要记录模型与生成设置。同样的问题换一个模型，得到的行为可能不同。

### 8.2 文件很长，为什么不能一直往请求里塞？

模型处理文字时，会把它转换成较小的单位，叫 **token**。可以先把它理解为计算文字输入和输出规模的单位。它不固定等于一个字或一个词，具体数量取决于分词方式，实际用量要看服务返回的统计。[DeepSeek token 说明](https://api-docs.deepseek.com/quick_start/token_usage/)

回到本篇的两次请求：

| 请求  | 放进了哪些内容？                |
| --- | ----------------------- |
| 第一次 | 基础要求、用户问题、工具说明等。        |
| 第二次 | 除前面的相关信息，还增加了工具调用和文件文字。 |

第二次多了文件文字，输入就变长了。如果文件有很多页，或者之前聊了很久，带进请求的内容还会更多。

模型允许的上下文和输出长度都有相应限制，需要按所选模型的规则安排。更多内容也可能带来更多费用和等待时间。后续学上下文管理时，再处理哪些资料保留、哪些裁剪或整理成摘要。

### 8.3 为什么还要约定回答格式？

如果你直接看回答，一段自然语言通常就够了。但如果程序要在页面上分别显示“读取状态”和“文件内容”，最好让回答包含这两项明确信息，例如：

```json
{
  "status": "ok",
  "answer": "今天学习 Agent。模型提出工具调用，程序执行工具。"
}
```

这一小段表示：`status` 的值是 ok，`answer` 的值是文件文字。程序就能分别取出它们。这种按约定组织字段的回答，叫**结构化输出**。它描述的是回答正文；第 6 节消息外层的 `role`、`content` 仍由程序按消息格式组织。

要实现它，可以先用提示词说明格式，再根据模型服务的支持情况使用相应的输出约束，并在程序中检查结果。即使 JSON 能正常解析，也要检查 answer 是否确实来自所读文件。

调用模型时还可能遇到 `temperature`，用来调整生成的随机性；不同模型的支持情况和参数作用需要按服务说明确认。调低随机性不会自动解决读错文件或编造内容的问题，仍要检查实际过程。[DeepSeek API 参数说明](https://api-docs.deepseek.com/api/create-chat-completion/)

### 8.4 页面上的回答一段段出现，是请求了很多次吗？

不一定。假设同一次模型回复分三段到达：

| 到达次序 | 新收到的文字           |
| ---- | ---------------- |
| 第一次  | lesson.txt 的内容是： |
| 第二次  | 今天学习 Agent。      |
| 第三次  | 模型提出工具调用，程序执行工具。 |

界面把这三段接起来，就形成了一条完整回答。这叫**流式返回**：同一次请求的响应分批到达，界面可以边接收边显示。

本篇的“两次模型请求”，指的是执行工具前后分别请求一次模型。每次请求都可以有很多流式片段，不能把片段数量当作请求次数。

工具调用的参数也可能分批到达，例如先收到路径的一部分。本文采用的基本流程要在取得完整调用、检查参数后执行。阅读日志时，也应以最终完成的参数和消息为准。

**理解练习。** 界面更新了十次文字，能否据此说模型被请求了十次？

**参考答案。** 不能。可能只是一次回复分成十个片段。要统计请求次数，需要查看实际发起请求的记录。

## 9. 同一件事，为什么在不同记录里写法不一样？

前面主要使用 Pi 的字段名称。以后看模型 API 文档、Pi 消息或运行日志时，会发现相似信息的字段写法不同。先问清楚“正在看哪种数据”，就容易对应。

### 9.1 Pi 保存的工具结果，与发给服务的工具消息

例如，“call_1 这次调用返回了文件文字”，在 Pi 里可以写成消息 C：角色是 `toolResult`，对应编号放在 `toolCallId`。

DeepSeek 的 Chat Completions API 则使用下面这样的工具消息字段：

```json
{
  "role": "tool",
  "tool_call_id": "call_1",
  "content": "今天学习 Agent。模型提出工具调用，程序执行工具。"
}
```

仍然从两项信息看起：`role: "tool"` 表示工具结果，`tool_call_id` 表明对应 call_1。它们表达的信息与前面的 Pi 结果有关联，但字段名称和内容写法不同。[DeepSeek 工具消息字段](https://api-docs.deepseek.com/api/create-chat-completion/)

Pi 的模型接入层负责把内部数据转换成相应服务接受的形式。本文省略的时间戳、模型信息等，也需要在完整 Pi 消息中按规则准备，不能把教学摘录直接当成完整调用代码。[本地消息类型](../../pi/packages/ai/src/types.ts) · [Pi 官方消息文档](https://pi.dev/docs/latest/message-types)

### 9.2 事件在告诉我们“哪一步发生了”

除了消息，程序还会发出运行通知，称为**事件**。例如“这条模型消息生成完了”“准备执行 read”“read 已经结束”。界面可以用它显示进度，日志也可以把它保存下来。

下面三类数据可以这样区分：

| 看到的数据        | 主要记录什么？        | 本篇的例子                 |
| ------------ | -------------- | --------------------- |
| Pi 内部消息      | 问题、调用和结果分别是什么。 | B 写要读取的文件，C 写实际返回的内容。 |
| 模型 API 请求与响应 | 按服务的接口约定交换信息。  | 使用该接口要求的 role 和编号字段。  |
| Pi 事件        | 消息或工具执行到了哪一步。  | 开始执行、结束执行、某条消息完成。     |

先用表格看一组读取成功的事件。这里只选取五条，省略其他过程：

| 顺序  | 事件名                    | 用普通话怎样读？                              |

| 1   | `message_end`          | 模型的一条消息 B 完成，内容是 call_1 这次读取要求。       |
| 2   | `tool_execution_start` | 开始处理 call_1 的工具执行，参数中的路径是 lesson.txt。 |
| 3   | `tool_execution_end`   | call_1 对应的操作结束，返回文件文字，并且没有标记错误。       |
| 4   | `message_end`          | Pi 把结果整理成一条完整的工具结果消息 C。               |

## 11. 面试追问：用读文件的例子说明原因

1. **读取同一个文件，为什么有时需要请求模型两次，有时一次就够？**  
   如果让模型决定是否读取，第一次请求先让它提出 read 调用；程序读出文字后，第二次再让模型根据结果回答。如果应用事先确定要读 lesson.txt，就可以先读取，把文字和问题一起交给模型，通常一次请求就够。次数取决于程序怎样组织任务，不能把“两次”当成所有任务的固定要求。

2. **parameters 和 arguments 都与参数有关，它们有什么区别？**  
   可以把它们对应为“填写要求”和“本次填写内容”。例如，工具定义中的 parameters 规定必须提供文字类型的 path；模型这次生成的 arguments 填写 `path: "lesson.txt"`。Pi 还要检查填写内容是否符合要求，再执行读取。即使格式通过，文件仍可能不存在。

3. **同一个任务读取两个文件，为什么只记录工具名 read 不够？**  
   两次操作都叫 read，工具名无法指出某份结果来自哪个文件。给读取 lesson.txt 的调用编号 call_1，给读取 homework.txt 的调用编号 call_2，再让结果带上对应的 toolCallId，就能找回每次操作的参数。检查时应沿着“编号找到调用，再看调用路径”的顺序核对。

4. **工具执行结束，为什么还不能直接说任务完成得对？**  
   结束可能是成功，也可能是报错，需要先看 isError 和返回内容。即使读取成功，也可能打开了另一个目录里的同名文件，或者模型回答加入了文件中没有的信息。因此还要检查读取目标、实际结果和最终回答，才能判断是否符合用户要求。

5. **业务接口超时，为什么不能回答“没有复验记录”？**  
   超时说明这次查询没有正常取得结果，还不知道记录是否存在。只有在查询成功、范围正确、数据完整性得到确认等条件下，空结果才支持相应范围内没有查到记录的判断。接口失败时应说明暂时无法核实，再按规则重试或请求进一步确认，不能把技术故障当成业务事实。
