## 1. 学到什么程度就够？什么时候开始项目？

**保留十个主题，不平均用力，也不以读完十篇作为开始项目的条件。** 当前目标是能借助 AI 实现功能，自己理解关键行为、定位问题、验证效果；不要求背 API 参数、逐行读完 Pi 源码，或独立重写完整 Harness。

区分三种学习深度：

| 深度       | 怎样学习                        | 完成标准                   |
| -------- | --------------------------- | ---------------------- |
| **重点动手** | 学核心机制，运行最小实现，主动制造错误，再修改一处行为 | 能结合日志解释正常与失败过程，并验证修改结果 |
| **基础验证** | 理解模块解决的问题，完成一个小实验           | 能解释输入输出、使用边界和一种常见失败    |
| **按需深入** | 先了解用途，项目遇到具体问题后再实现          | 能说明为什么需要引入，并用测试检查收益    |

**第 3 篇完成一次最小循环练习后，就开始候选项目。** 第 4 篇的工具可靠性、第 8 篇的基础评测、第 9 篇的权限边界同步学习；不必等待所有章节生成。

生成进度、学习进度和项目能力分开记录。已生成不代表已掌握，篇数也不代表求职准备程度。项目笔记按实际产出整理，不额外规定必须写满多少篇。

**主题重要，不等于项目必须包含对应模块。** 引入模块前先回答：现在遇到了什么问题？简单方案为什么不够？准备怎样验证它有帮助？

MCP 用于规范应用与外部能力的交互，不替应用设计推理、上下文和业务权限。先理解普通工具调用，再按需接入。[MCP 官方架构说明](https://modelcontextprotocol.io/docs/learn/architecture)

## 4. 实际学习顺序与阶段验收

### 阶段一：用第 3 篇验证前两篇的理解

先运行现有最小循环，再沿日志查看“模型请求 → 工具执行 → 结果回传 → 最终回答”。模拟模型用于观察程序行为；接入真实模型后，还要单独验证工具选择和回答质量。

验收时至少完成：

- 运行正常读取、文件不存在、参数错误、达到最大步数的情况，并指出失败发生在哪里。
- 修改一个工具或停止条件，先预测结果，再运行验证。
- 用自己的话解释为什么模型提出工具调用后，还需要程序实际执行工具。
- 按需补函数、对象、数组、异常和异步语法，能读懂并修改关键分支；不要求背完整程序。

满足后即可开始候选项目，不必等第 4～10 篇全部完成。

### 阶段二：开始项目，同步学习第 4 篇和第 8、9 篇的基础部分

把读文件工具换成业务查询工具，先做一条小任务链路。同步补参数校验、失败处理、访问范围和逐步日志。

先保存约 **5～10 个固定样例**，覆盖正常、查不到、工具失败、证据不足和越权请求。数量是启动建议，关键是每个样例有明确的预期行为。模型调用失败、工具失败与业务资料不足要分别记录。

完成标准：能演示任务，复现一次失败，从日志解释原因，并验证修复。接入真实模型验证后，再描述项目的 Agent 效果；模拟模型实验只证明相应程序流程。

### 阶段三：按项目问题补第 5～7 篇

先掌握第 6 篇的上下文与会话基础；需要文档检索时深入第 5 篇，需要中断恢复或人工审批时深入第 7 篇。业务只需单次查询时，可以保持简单流程。

每次只解决一个明确问题，用原有样例和新增失败样例检查改动。能解释为什么采用、为什么暂缓某个模块，也是学习成果。

### 阶段四：完善评测与最小交付

系统学习第 8 篇，并落实第 10 篇的最小运行方式。完成标准是：

- 别人能按照说明运行项目；配置、依赖和密钥使用方法清楚。
- 有固定测试集、基线对比和若干失败案例，指标填写真实测量结果。
- 能讲清数据来源、权限边界、关键实现、AI 与框架承担的工作。
- 能解释一次改进的收益、代价和局限。

达到这些标准后即可整理简历并开始投递，根据目标岗位反馈继续补齐，不以全部扩展功能完成为前提。

## 5. 候选项目怎样开始？

优先验证已有方案：**旧改交付诊断 Agent**，原方案见 [[2026-11-07-pi-delivery-diagnosis-design]]。任务是查询报验、整改和复验记录，解释“整改已提交，为什么还不能交付”，输出阻塞原因与证据编号。

第一版范围控制为：**输入问题与项目编号 → 只读查询记录 → 核对证据 → 输出诊断或信息不足说明。** 沿用模拟数据和 Node.js / TypeScript，不同时重写多套实现。

先做一个小实验，确认愿意理解业务、能构造合理数据，并能判断答案对错。特别检查：引用是否属于当前项目、是否关联本次整改、旧复验结果能否支持当前结论。保留固定规则或单次模型请求作为基线，判断 Agent 增加了什么价值。

如果暂时只查询结构化记录，先使用查询工具；需要从规范文档查依据时，再引入 RAG。有明确失败恢复、审批或外部接入需求时，再增加对应模块。

若不适合这个业务，再考虑代码库问题定位助手，或文档与业务记录联合助手。选择依据是：任务明确、数据可获得、结果能检查、愿意持续改进。

## 6. 项目怎样积累成简历素材？

### 第一版：链路可运行、行为可观察

完成只读查询与有证据的回答，保留工具参数、结果、最终结论和少量固定样例。通过改变记录检查结论是否变化。

### 第二版：能验证正确性、解释一次改进

对证据编号、项目归属、整改关联做程序检查。检查失败时返回具体原因，允许有限补查或修正。

逐步扩大测试集，按实际情况增加到约 30～50 个案例；不把数量当硬性门槛或统计充分性的保证。覆盖正常通过、当前整改未复验、引用旧记录、查询失败、证据不足和越权等情况。

开发与调试案例、暂不参与调优的测试案例分开。比较时固定数据、模型标识、提示词版本与运行配置，记录正确性、失败类型、延迟、调用量与可测得的费用。

### 第三版：围绕瓶颈升级并交付

检索不准就改检索，历史混乱就改上下文，任务中断就改状态恢复，难以复现就完善运行说明。评测没有体现收益的复杂模块，可以暂缓或移除。[Anthropic：长任务 Harness 设计](https://www.anthropic.com/research/harness-design-long-running-apps)

最终保留：可运行代码、运行说明、简洁架构图、数据与评测说明、一次真实前后对比、几个能解释的失败案例。明确标注模拟数据，不虚构成功率、成本或个人贡献。

项目笔记随实践整理，覆盖选题与设计、关键实现与失败处理、评测与改进即可，不要求额外写满三篇长文。

## 7. 怎样使用 AI，同时积累自己的能力？

**AI 可以起草实现，你要逐步掌握需求、关键行为与验证方法。** 不要求不用 AI 重写全部代码，但要能独立解释关键流程，读懂并修改项目用到的基础逻辑。

| 可以交给 AI 起草 | 自己必须逐渐能判断 |
| --- | --- |
| API 接入、数据转换、数据库操作、日志和框架配置 | 输入输出是否符合任务，数据是否可靠，哪些能力由框架提供 |
| 重试、会话、工具执行等模块代码 | 哪些失败能重试，重复执行有什么后果，会话是否串用 |
| 测试代码与结果汇总 | 预期答案从哪里来，案例是否真的覆盖失败，改动是否有效 |
| 实现方案与技术解释 | 为什么需要该模块，简单方案是否足够，能否结合日志复述 |

每次小改动按“先说明预期 → AI 辅助实现 → 阅读关键差异 → 运行正常和失败情况 → 解释结果”的顺序进行。不要只凭 AI 自报完成或模型给自己的评分验收；能够用规则、已知答案和实际操作验证的部分，优先使用这些依据。

同时并行补齐：

- **一门主力语言**：函数、对象或字典、数组、条件、循环、异常和异步请求，能修改真实项目逻辑。
- **开发与后端基础**：Git、命令行、依赖、HTTP、JSON、日志、数据库查询，以及项目涉及的并发和任务状态。
- **大模型基础**：token、上下文容量、Embedding、生成随机性，以及训练、微调、推理的区别。
- **求职准备**：按岗位练习编程题，练习讲清问题、方案、个人贡献、验证与局限。

若继续 TypeScript 项目，不要求同步维护 Python 版本；目标岗位要求 Python 时，逐步补文件处理、接口、日志和测试。若语法基础不熟，把短练习单独补充，避免每篇 Agent 笔记都展开一遍语言入门。

转向算法或推理岗位时，再按职责单独补 PyTorch、Transformer、训练与强化学习，或推理服务等知识。

## 8. 后续笔记统一采用怎样的格式？

**采用“核心讲解＋最小实验＋按需查阅”，正文优先让人看懂，不追求篇幅和源码覆盖率。**

### 正文：围绕一个问题，只讲当前必需内容

1. **具体问题**：没有这个模块，会出现什么失败？使用一个贯穿案例。
2. **两三个核心概念**：先解释现象，再引入术语。
3. **一条流程**：说明谁接收什么、做什么、输出什么；图只画当前链路。
4. **最小实验**：正常情况和一种典型失败；代码聚焦关键行为，运行方式明确。
5. **一次小修改与自测**：先预测行为，再验证；能解释设计取舍和失败原因。

基础验证章节做到这里即可；重点章节再逐步增加必要失败场景。按需深入的章节先讲用途和适用条件，进入项目实现时再展开。

### 按需查阅：放到文末，使用折叠内容

- 完整可运行代码、安装配置与排错步骤。
- 新出现的语言语法、额外 API 字段。
- 框架源码对照、版本差异与进阶实现。

教学示意数据、真实 API 格式和 Pi 内部消息分别标明。源码用于核对关键机制，不把逐行讲解整个框架作为完成要求。外部事实参考官方资料，实验写清验证范围，模拟运行与真实模型效果分开说明。

**现有第 3 篇的使用方式：** 先了解目标与消息流程，运行完整示例；根据日志回看工具执行、循环和错误处理的关键片段。函数、异步等内容不熟时再补对应小节，不要求顺序背完所有代码。需要重写该篇或生成第 4～10 篇时，按本节格式执行。
