# Pi 旧改交付诊断 Agent

## 第一版

做一个可以在终端运行和观察的学习项目。输入「P001 的整改已经提交，为什么还不能交付」，Pi 根据模拟记录给出阻塞原因、证据编号和建议处理角色。以一次完整的模型、工具、模型往返为第一个里程碑。业务样例和规则均为模拟数据。

## 运行方式

使用 Node.js、TypeScript 和 Pi Coding Agent CLI。Pi 作为项目级 npm 依赖，采用固定版本和锁文件。用 `--extension` 显式加载本地扩展，用 `--tools` 选择业务工具，使用 `--no-mcp` 关闭 MCP 接入。模型使用 Pi 的 DeepSeek provider，通过本机 `DEEPSEEK_API_KEY` 配置。项目的第一个入口是终端，JSON 模式用于查看事件。

## 数据和工具

首版提供一个 `get_node_history` 只读工具。工具接受项目编号和可选的施工节点编号，返回该范围内的报验、整改、复验记录。记录包含自身编号、父记录编号、节点编号和状态。工具明确区分查无项目、查询失败，以及成功查到完整历史但相关记录为空。

第一个案例的数据包括一条报验、一条已提交的整改，以及一条只关联上一次整改的历史复验。本次整改没有对应复验。模型应根据关联关系判断待监理复验，结论引用本次整改编号。数据查询模块独立于 Pi 扩展，后续可接旧改系统的只读接口。

## 边搭边学

1. 启动 Pi，提交一句普通问题，确认模型配置可用。了解 CLI、会话和模型供应商各自做什么。
2. 注册 `get_node_history` 并加载模拟数据。从 JSON 事件中找到工具名称、调用参数和返回结果，顺着轨迹读出 Agent 循环。
3. 在第一条链路稳定后加入 `submit_diagnosis`，检查引用记录是否在本次查询结果里、是否属于当前项目、是否关联本次整改。构造一条引用旧复验记录的提交，让校验返回具体原因，观察模型是否补查或修正结论。
4. 增加三个回归场景，覆盖当前复验已通过、历史复验通过但当前仍待复验，以及查询失败后应报告待核实。旧改真实接口可用后，补做权限差异案例。

## 首个里程碑的验收

- 用一条项目命令启动模拟案例，得到「待监理复验」和本次整改记录编号。
- JSON 事件包含 `get_node_history` 的一次实际调用及结果，可以从报告定位到来源记录。
- 换成已有本次复验记录的样例后，结论随工具数据变化。
